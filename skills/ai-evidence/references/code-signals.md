# Code signals

Everything here comes from `analyze_code.py` (standard library only; Python is parsed with `ast`, which never imports or runs anything) and from what the model notices when it reads the code. It never runs `git` and never executes, installs or imports the code.

**Read this first.** Using AI to write code is normal and legitimate, and often good practice. This report says which traces exist. It does not say the code is good or bad, or the work honest or dishonest, and it must not be used to accuse anyone. For quality, use `code-teardown`.

Two kinds of evidence, not alike:

- **Residue** is something an assistant leaves behind that a person does not usually write. It is the strong kind, but it shows that an assistant took part, not how much of the code it wrote.
- **Style** is a habit of how assistants write and also how many people write. Formatters, linters, templates, scaffolding tools, tutorials and copied snippets all produce uniform, heavily commented code, and an assistant can be told to write in any style. Style items are weak and share one capped budget (total weight 0.5 per question).

Code can be fully AI-written and show none of this. The absence of traces is never evidence of a human author.

## The two questions

- **Largely written by AI?** (`generated`): most of the code came from an assistant.
- **Built with AI assistance?** (`ai_edited`): an assistant took part in some way. Configuration files and commit trailers answer this one, not the first.

Pattern definitions, tests and the docs of detectors contain these very phrases. So residue is only looked for on **whole-line comments** (or bare `...` lines), never in strings or regular expressions.

| `cd-comment-density` | 6 / 0.1 | 0.35+ comment lines per code line | Documented libraries and teaching code |
| `cd-step-comments` | 6 / 0.1 | Three or more "Step N:" comments | Scripts written as walkthroughs |
| `cd-emoji-in-code` | 6 / 0.1 | Five or more pictographs (✅ ❌ 🚀 ✨...) in code and messages. Plain symbols like ✔ ◆ do not count | Some CLIs use them on purpose |
| `cd-docstring-uniformity` | 6.5 / 0.12 | Python, 10+ functions: 90 % documented and 60 % with Args/Returns, or five or more tiny functions with Args/Returns | A docstring linter enforces the same |

| `cd-skipped` | 5 / 0 | Fewer than 200 code lines | Says why no style item appears |

## History (only with a log you export)

Git is never run by the script. A repository's own configuration can make git launch programs, so **you** run the export, on a repository you trust, and give the script the file:

```
git -C <repo> -c core.fsmonitor=false -c core.pager=cat --no-pager log --reverse --numstat --no-renames \
  --format='%x1e%H%x1f%aI%x1f%s%x1f%b%x1d' > git-log.txt
```

The format has **no author names and no e-mail addresses**, and the script reports none. Besides the trailers above:

| id | Score / weight | Condition | How it misleads |
| --- | --- | --- | --- |
| `cd-history-shape` | 6 / 0.1 | 5 commits or fewer, 500+ added lines, 70 %+ in the first | Imported or squashed code looks the same |
| `cd-history-bursts` | 6 / 0.08 | 15+ commits, 40 %+ within two minutes of the previous one | Scripts, rebases and small steps |
| `cd-commit-style` | 6 / 0.1 | 10+ commits, 90 %+ conventional, average body 200+ characters | Disciplined teams with templates |
| `cd-messy-history` | 3 / 0.1 | 15 %+ of commits are "wip", "typo", "update"... | An assistant can imitate it |

## Informative only

`cd-generated-code-headers` (weight 0): files marked "Code generated ... DO NOT EDIT", from protoc, OpenAPI generators and similar. They are machine-made, not AI-made, and are left out of the style statistics.

## What the model adds

The model reads the code and records up to six observations (`--visual observations.json`). Weight caps by kind:

| `kind` | Cap | Look for |
| --- | --- | --- |
| `hallucinated_apis` | 0.35 | Calls to functions, methods, flags or packages that do not exist in the library or version in use, imports of packages that look invented. Check against what is in the repository; do not go online unless asked |
| `human_idiosyncrasy` | 0.3 | Domain shortcuts, odd but purposeful structure, local conventions, comments that refer to past incidents, uneven polish. Points **away** from AI. Assistants can fake it |
| `generic_scaffolding` | 0.25 | Boilerplate that fits any project, abstractions with a single user, defensive code for cases that cannot occur |
| `code_other` | 0.2 | Anything else; explain it |

## What is not here

- **Dependencies that do not exist** on the package registries ("slopsquatting" risk). Needs the network.
- **Whether the code works or is good.** See `code-teardown`.
- **Comparison with the author's other code**, the most robust approach to the question "did this person write this".
- **Other languages' syntax trees.** Python gets docstring analysis; other languages get comment statistics only.

## Using it responsibly

A trace of AI is not a flaw. Do not use a result to accuse anyone, to grade a student, or to penalise a contributor. Use it to understand how a project was made, and where a human review is worth the time.

## Running it

```
analyze_code.py <project-dir|file> [--git-log git-log.txt] --out $WORK/evidence.json
```
